# AnsiView 2.0 Screen Designer: BBS Menus and Screens Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline) with superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Owner brief section 4: make it easy for SysOps to design main menus, login and welcome screens, goodbye screens, bulletins, message and file area headers, door menus, ANSI ads and loading screens; insert BBS display codes from a picker and preview them with sample values; start from templates and reusable components; preview exactly what a caller sees at a chosen baud; export straight into a BBS install folder with the file names each package expects, and upload through the terminal's file transfers. Owner addition (coordinator, 2026-10-30): "I want to be able to work with ALL BBS's".

**Architecture:** Pure logic in `Packages/AnsiCore/Sources/AnsiCore/Screen/`: a table-driven package registry (`BBSPackages.swift`), the display code catalogue (`DisplayCodes.swift`), the BBS side renderer and colour code encoder (`BBSDisplay.swift`, reusing `BBSCodes.sgr`), export profiles and the exporter (`ScreenExporter.swift`), the folder writer with `.bak` (`ScreenExportWriter.swift`), the screen set (`ScreenSet.swift`), caller preview checks (`CallerPreview.swift`), templates (`ScreenTemplates.swift`), components and the user component store (`ScreenComponents.swift`, `ComponentStore.swift`), encodings (`ScreenEncoding.swift`) and hints (`ScreenDesignerHelp.swift`). The app adds `App/ScreenDesigner*.swift` windows (template gallery, code picker, sample values, component library, caller preview, export profiles, screen set, upload) and two menu hooks: File > New from Template... and a Screen menu. Editor files get only a component insert hook through the existing floating paste (`CanvasEditor.beginFloating`).

**Tech Stack:** Swift 5 mode, Swift Testing, AppKit, XcodeGen.

## Rulings (each with its cost if wrong)

0. **All BBSes (owner, through the coordinator).** Every package that can be documented from real sources is registry data: 20 packages (the 7 of the brief plus Telegard, Iniquity, Oblivion/2, Impulse, Celerity, RemoteAccess, ProBoard, QuickBBS, Spitfire, Searchlight, DayDream, Talisman, Maximus). Those that cannot are listed as not yet supported in `docs/BBS-COMPAT.md` with what is missing. Retro platforms are left to the terminal emulation plan (seam: ruling 1). Cost if wrong: a package documented only in sources not found (PCBoard's file names, Wildcat's macros, Telegard's colour table) needs a later data entry.

1. **Packages are data.** `BBSPackage` is a string identified value; each one is a `BBSPackageDefinition` (colour syntax family, macro syntax families, code table, file rules, sources) in `BBSPackageRegistry.definitions`. The renderer, encoder and foreign code check work on the syntax families, so a package whose syntax is already known is a table entry plus tests. Packages without real sources go in `docs/BBS-COMPAT.md` as not yet supported. Retro platforms (PETSCII, ATASCII, Viewdata, Apple II) belong to the terminal emulation plan; the seam is `TextEncoding` plus `ColourSyntax.none` and the exporter's encoding step, which is the only place that assumes CP437 bytes. Cost if wrong: a package with a syntax unlike every family needs a new enum case and renderer branch.
2. **Codes are text in the art.** The picker inserts a code's exact characters at the cursor (Ctrl-A and heart codes as the control byte, drawn as their CP437 glyph). Nothing hides them in the editor; Sample Values Preview and Preview as Caller show them substituted. Cost if wrong: SysOps who expect a field object must edit text; but files stay byte exact to what the BBS reads.
3. **Colour codes both ways.** Export can write colours as ANSI escapes or as the package's own codes (`ColourCodeMode`). Open with BBS Codes... reads such a file into the editor (colours become cells, value codes stay text). Round trips are tested for every package. Cost if wrong: none for ANSI (the default).
4. **The BBS side is simulated, not emulated.** `BBSDisplay.render` turns a file into what the BBS sends: colours to SGR, value codes to sample values (with documented padding), clear screen and new line to their effect, pause/beep/delay ignored, unknown codes left as text, stop at 0x1A. Cost if wrong: a code with BBS specific side effects (Synchronet `@GOTOXY@`, Mystic `|[X##`) shows as text in the preview; they are not in the catalogue.
5. **Animated screens export as ANSI.** Animations use cursor movement and padding (animation plan); package colour codes cannot move the cursor, so a native profile still writes ANSI and says so (`animatedAsANSI`). Cost if wrong: none; BBSes display ANSI files.
6. **Never overwrite silently.** Export asks before replacing a file and writes atomically; the first file replaced goes to `<name>.bak`, which is never overwritten (usually the SysOp's original), and later replacements keep the previous version in `<name>.bak2` (review fix: one generation lost the original after two exports). Paths are checked to stay inside the folder; Export Again writes exactly the file the screen set names. Cost if wrong: versions between the original and the previous one are not kept.
7. **Screen set per profile.** The "project level screen set" is kept per export profile (one BBS install), as JSON in Application Support: slot, file name, source file bookmark, SHA-256 and time of the last export. Status compares the source's export now and the file in the folder: Not exported, Exported, Modified since, Changed in the BBS folder, Missing, Source not found. Cost if wrong: a SysOp who wants one set across two BBSes keeps two sets.
8. **Line ends CR LF by default** (no package documents them; DOS era files use CR LF); LF is a profile option. SAUCE is on by default only for packages documented to stop at it (Synchronet, ENiGMA). Cost if wrong: an LF only BBS on Unix shows doubled line ends until the profile is switched.
9. **Caller preview uses the real emulator.** Preview as Caller feeds the rendered bytes (UTF-8 converted when chosen) through `LinePacer` at the chosen baud into `TerminalEmulator`, drawn with `AnsiRenderer`. Layout warnings come from `CallerPreviewAnalysis`, which follows the cursor the way an immediate wrap terminal (ANSI.SYS) does, because AnsiView's own emulator has a delayed wrap and would hide the column 80 problem. Cost if wrong: warnings may be stricter than a SyncTERM caller needs.
10. **Templates leave the last column and last row free** (23 rows for 80 x 24, 36 for 132 x 37), and keep value codes out of framed rows, because a value longer than its code pushes the frame edge. A test exports every template for every package at every width and requires no layout warnings with sample values.
11. **Upload reuses transfers.** Upload via Terminal copies the exported bytes to a temporary file with the BBS file name, opens (or reuses) the terminal of the chosen dialing directory entry and, when the user says the BBS is ready, calls `TerminalTransfers.startUpload(files:kind:)` with the entry's protocol. Cost if wrong: one extra click compared with an automatic start; but uploading before the BBS asks would fail.
12. **Templates' value codes fall back to sample text** when a package has no code for that value (Wildcat has none documented), so every template reads correctly everywhere.

## Deferred minors (from the final review)

- Stale bookmark flags are not refreshed (`TransferFolders.resolve` ignores `isStale`).
- Drawn smileys and hearts (0x01, 0x03) go out raw; Synchronet reads a smiley followed by a letter as a Ctrl-A code, WWIV a heart and digit as a colour; the foreign code check reports them for other packages.
- Celerity literal "|d" style text is not doubled (the typed code check is case blind for MECCA's sake).
- Lowercase forms of case blind codes (`%un`) are not reported by the foreign code check.
- Case sensitive network shares: `MAIN.ANS` and `main.ans` are different files there, so no replace prompt appears; `.bak` names are not 8.3.
- SAUCE data type stays 1 (character) for Ctrl-A, MECCA and UTF-8 bodies.
- Picker, component and code tables render their rows only after the first draw in the offscreen harness (the second capture shows them); not seen as a problem in a live window, but not observed live either.
