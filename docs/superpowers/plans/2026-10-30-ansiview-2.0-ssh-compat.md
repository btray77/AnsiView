# AnsiView 2.0: SSH Compatibility with Classic BBS Servers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline) with superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner's choice "Extend SwiftNIO SSH": the terminal's SSH transport connects to classic BBS SSH servers (Synchronet and other cryptlib boards, ENiGMA 1/2) as well as OpenSSH, by vendoring a patched swift-nio-ssh 0.15.1 that adds finite field Diffie-Hellman key exchange (group14, group16, group exchange), RSA host keys (Security framework), AES-CTR/CBC with HMAC, and keyboard-interactive login. No C code, sandbox friendly.

**Architecture:** `Packages/swift-nio-ssh-bbs` is upstream swift-nio-ssh 0.15.1 (commit `d1985926494b624e751b379009dc83f3395fd88a`, Apache 2.0, `LICENSE.txt` kept) with the example executables and benchmarks left out. New code lives in new files (`SSHBigUInt.swift`, `DiffieHellmanGroups.swift`, `DiffieHellmanKeyExchange.swift`, `SSHKeyDerivation.swift`, `NIOSSHRSAPublicKey.swift`, `AESCBCCTRTransportProtection.swift`, `KeyboardInteractive.swift`, `NIOSSHNegotiatedAlgorithms.swift`); the edits to upstream files are routing and enum cases, each listed in `PATCHES.md` so the copy can be rebased. `project.yml` (and the App Store spec) point the existing `swift-nio-ssh` package key at the local path, so the app's target dependencies do not change. `App/SSHTransport.swift` answers keyboard-interactive prompts (Keychain password, else a sheet), logs the negotiated algorithms and names the unsupported category when negotiation fails.

**Tech Stack:** Swift, XCTest (in the vendored package, like upstream), Swift Testing (AnsiCore), CryptoKit/swift-crypto (hashes, HMAC), CommonCrypto (AES block modes, a system framework, no C code of ours), Security framework (RSA verification), SwiftNIO 2.104.0.

## Rulings (each with its cost if wrong)

1. **Vendor, do not fork on GitHub.** The copy is a local SwiftPM package with the upstream directory layout; every change to an upstream file is listed in `PATCHES.md` with the reason. New behaviour is in new files. Cost if wrong: a rebase on a future upstream touches about a dozen small hunks.
2. **Big integers in our own Swift.** `SSHBigUInt` is a fixed width little endian `[UInt64]` number with Montgomery multiplication (CIOS); modular exponentiation is a Montgomery ladder over a fixed number of exponent bits with a masked (branch free) conditional swap and a masked final subtraction, so the work done does not depend on the secret exponent's bits. No vetted constant time pure Swift big integer library exists (attaswift/BigInt is MIT but variable time). Cost if wrong: a timing side channel on a per connection ephemeral exponent.
3. **Private exponent: 512 random bits with the top bit set** (twice the 256 bit security of the strongest cipher, as OpenSSH sizes it), so the ladder always runs 512 steps. Cost if wrong: none for security; a few milliseconds.
4. **Value checks.** The server's `f` must satisfy 1 < f < p - 1 (RFC 4253 section 8, RFC 8268); a group exchange `p` must be odd and 2048 to 8192 bits, and `g` must satisfy 1 < g < p - 1. Primality of a group exchange `p` is not tested (OpenSSH's client does not either). Cost if wrong: a malicious server could choose a weak group, but it already holds the session.
5. **Group exchange request** min 2048, preferred 3072, max 8192 (RFC 4419; RFC 8270 raises the minimum to 2048). Cost if wrong: a board with only a 1536 bit group fails with a plain message.
6. **Not added:** 3des-cbc, diffie-hellman-group-exchange-sha1, diffie-hellman-group1-sha1, hmac-md5, the -96 MACs, and the -etm MAC variants. No measured board needs them; -etm is left out because CBC with EtM is the Terrapin (CVE-2023-48795) vulnerable combination and we do not implement strict key exchange. Cost if wrong: a board that offers only one of them fails with a message naming it.
7. **Preference: modern first.** Key exchange: curve25519-sha256, curve25519-sha256@libssh.org, ecdh-sha2-nistp384, nistp256, nistp521, diffie-hellman-group16-sha512, diffie-hellman-group-exchange-sha256, diffie-hellman-group14-sha256, diffie-hellman-group14-sha1. Host keys: ssh-ed25519, ecdsa-sha2-nistp384/256/521, rsa-sha2-512, rsa-sha2-256, ssh-rsa. Ciphers: aes256-gcm@openssh.com, aes128-gcm@openssh.com, aes256-ctr, aes192-ctr, aes128-ctr, aes256-cbc, aes128-cbc. MACs: hmac-sha2-256, hmac-sha2-512, hmac-sha1 (AES-GCM ignores the MAC). The server side of the vendored library (used only by tests) never offers group exchange. Cost if wrong: an OpenSSH server keeps negotiating curve25519, ed25519 and AES-GCM (proved in the OpenSSH run).
8. **RSA host keys** are verified with the Security framework: the SSH blob's `e` and `n` become a PKCS#1 `RSAPublicKey` DER for `SecKeyCreateWithData`, and `SecKeyVerifySignature` checks `rsaSignatureMessagePKCS1v15SHA1/256/512` over the exchange hash. The signature's algorithm name must equal the negotiated host key algorithm (RFC 8332), and the key's type must be `ssh-rsa` for any of the three. Moduli from 1024 to 16384 bits are accepted (OpenSSH's floor is 1024). The key blob is kept byte for byte, so the exchange hash and the known hosts fingerprint use exactly the server's bytes. Cost if wrong: an RSA host key with a non canonical encoding is still compared and fingerprinted exactly as sent.
9. **ssh-rsa (SHA-1) signatures** are accepted only when the server offers neither rsa-sha2-512 nor rsa-sha2-256 (last in preference). Cost if wrong: SHA-1 over the exchange hash of a live session is not a practical forgery target.
10. **Key derivation** follows RFC 4253 section 7.2 including the key extension `K2 = HASH(K || H || K1)`, now also in the elliptic curve exchange (upstream assumed one digest is always enough, which is false for hmac-sha2-512 after SHA-256 or any 32 byte key after SHA-1). Cost if wrong: none (only lengths that upstream never used change).
11. **Keyboard-interactive (RFC 4256).** Order: key file, password, keyboard-interactive, none. A request whose prompts are a single hidden prompt that mentions "password" is answered with the Keychain password once per connection; a request with no prompts is answered at once; anything else (or a second password prompt, or no saved password) shows a sheet with the server's name, instruction and prompts (secure fields for hidden ones). Cancel ends the login with a plain message. Answers are never stored. Cost if wrong: the user types the password into the sheet once.
12. **Negotiated algorithms are reported** by a new `NIOSSHNegotiatedAlgorithmsEvent` (user inbound event after each key exchange). The app logs it with `os.Logger` (subsystem `com.traynham.AnsiView`, category `ssh`) and keeps it on the transport (`negotiated`). Cost if wrong: none.
13. **Plain errors.** "The server only offers SSH methods AnsiView cannot use yet" now names the category (key exchange, host key, cipher or MAC) and the server's list for it, and only appears when no supported algorithm is in common.

## Review Focus

- Constant time exponent loop (no branch on secret bits), range checks on `f`, `p`, `g`; RSA signature algorithm bound to the negotiated one; RSA key type check; MAC compared in constant time; CBC/CTR packet length checks (multiple of the block size, minimum size, maximum size) before allocation; MAC verified before the payload is used.
- Message 31 (`KEX_DH_GEX_GROUP` vs `KEXDH_REPLY`) and 60 (`USERAUTH_INFO_REQUEST` vs `PK_OK`) are told apart by structure and by the exchange in progress; fuzzed.
- Known hosts fingerprints for RSA keys identical to `ssh-keygen -lf`.
- Transfers over SSH keep working (ZMODEM download with legacy algorithms in the terminal harness).
