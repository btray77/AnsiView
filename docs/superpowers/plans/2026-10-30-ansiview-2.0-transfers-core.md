# AnsiView 2.0 Transfers Core: File Transfer Protocol Engines Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline) with superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver owner brief section 3 (file transfers) at the engine level: XMODEM (checksum, CRC, 1K), YMODEM (batch, and YMODEM-G), ZMODEM (full, with crash recovery and auto start detection) and Kermit, as transport agnostic state machines in AnsiCore, with a sandbox safe file side, a telnet wrapper, a session type the terminal plan will wire in, and a command line driver that proves interoperability against lrzsz and C-Kermit.

**Architecture:** Every protocol is a pure state machine class (`TransferEngine`): bytes from the line go in through `receive(_:)`, bytes to send come out of `takeOutput(max:)` (streaming senders generate lazily, so the caller's write speed is the flow control), timers run off an injected `TransferClock` and fire from `tick()`, and progress, file and error events come out of `takeEvents()`. No sockets, threads or `Date()` calls inside an engine. Files go through two small protocols: `TransferSink` (receiving, implemented by `DownloadsDirectorySink`, which sanitizes names and writes only inside a chosen directory) and `TransferSource` (sending). `FileTransferSession` wraps one engine with a clock, rate and ETA, an event log and SHA-256 results; `TransferStartDetector` spots a ZMODEM or Kermit start in terminal output; `TelnetTransferChannel` puts an engine on a `TelnetSession`. The `ansixfer` executable (an AnsiCore package product, never in the app bundle) runs an engine over stdio, a pipe to a child process, a pty, or TCP.

**Tech Stack:** Swift 5 mode on the Swift 6.3 toolchain, Swift Testing, CryptoKit (SHA-256), Darwin (`posix_openpt`, `poll`, sockets in the CLI only).

**Spec:** `docs/STUDIO-CHECKLIST.md` section 3 and the coordinator's brief for `ansiview-2.0-transfers-core` (copied into the rulings).

## Rulings

1. **Engine contract.** `start()`, `receive(_ bytes:)`, `tick()`, `takeOutput(max:)`, `takeEvents()`, `cancel()`, read only `status` (`idle`, `running`, `completed`, `failed(reason)`, `cancelled`) and `progress` (current file, bytes, size, total bytes). Engines never block and never read the clock except through `TransferClock.now`. Cost if wrong: a later refactor of the session layer, not of the protocols.
2. **Timeouts and retries (defaults, all in `TransferOptions`).** XMODEM/YMODEM: receiver sends its start character every 3 s (10 tries with `C`, then falls back to NAK for plain XMODEM if checksum is allowed), 10 s per block, 10 retries per block; sender waits 60 s for the start. ZMODEM: 10 s per header wait, 10 retries, 20 consecutive ZRPOS without progress is a failure. Kermit: 10 s packet timeout, 10 retries. Cost if wrong: slow recovery on a bad line.
3. **XMODEM padding.** Plain XMODEM has no length. The receiver holds the last block until EOT and then (default `stripTrailingSUB`) drops trailing 0x1A bytes of that block only; `keep` writes it as received. YMODEM uses the announced size and truncates exactly. A binary file that really ends in 0x1A loses those bytes over plain XMODEM with the default; this is the classic limitation and is reported, not hidden. Cost if wrong: one option default.
4. **XMODEM details.** Blocks SOH (128) and STX (1024) are both accepted by every receiver mode. A repeated block (number one less than expected) is ACKed and dropped; any other out of sequence block cancels. Two consecutive CAN at a block boundary cancel. A bad block triggers a 1 s purge (wait for line silence) then NAK. EOT is NAKed once and ACKed on the repeat in YMODEM (the spec's figure), ACKed at once in XMODEM. Our sender resends EOT on NAK. XMODEM-1K sends 128 byte blocks when 896 bytes or fewer remain.
5. **YMODEM header.** Block 0 is `name NUL size mtime(octal) mode(octal) 0 NUL`, NUL padded to 128 (1024 if longer). An empty name ends the batch. YMODEM-G: the receiver sends `G`, the sender streams blocks without waiting, the receiver never ACKs data and cancels on any error. Exact ACK behaviour for block 0 and EOT is checked against `lsb`/`lrb` in Task 9 and recorded.
6. **ZMODEM framing.** Hex headers (lowercase hex, CRC-16, `CR LF|0x80` then XON except after ZACK and ZFIN), binary16 (`ZBIN`) and binary32 (`ZBIN32`) headers, data subpackets ending ZCRCE, ZCRCG, ZCRCQ, ZCRCW with the CRC of data plus the end byte. CRC-32 is used when the receiver sets CANFC32 and the sender allows it. ZDLE escaping always covers ZDLE, DLE, XON, XOFF and their high bit forms and CR after `@`; ESCCTL (asked by the receiver's ZRINIT, or sent by our sender in ZSINIT TESCCTL) escapes every control character; `escapeTelnet` escapes 0xFF (as ZRUB1) and CR. Raw XON/XOFF are ignored by the decoder. ZRLE (`ZBINR32`), ZCHALLENGE, encryption and ZCOMMAND execution are not implemented; a ZCOMMAND is refused with ZCOMPL status 1 and never run.
7. **ZMODEM flow.** Sender: `rz\r` plus ZRQINIT, waits ZRINIT, optional ZSINIT, ZFILE (ZF0 = ZCBIN, or ZCRESUM when resume is asked) with the file info subpacket, then ZDATA streamed with ZCRCG, ZCRCE at the end then ZEOF; a nonzero ZRINIT buffer size makes it end each window with ZCRCW and wait for ZACK. ZRPOS restarts at the asked offset; ZSKIP moves to the next file; ZFIN, wait ZFIN, then `OO`. Receiver: ZRINIT (CANFDX, CANOVIO, CANFC32, ESCCTL if set, buffer size 0 or the configured window), ZRPOS with the resume offset or 0, ZSKIP when the sink refuses, ZRPOS on any bad subpacket or out of place data, ZACK on ZCRCQ and ZCRCW, ZRINIT after a good ZEOF, ZFIN answered with ZFIN. Cancel is 5 consecutive CAN; we send 10 CAN and 10 backspaces (the lrzsz `canit` string). Subpackets are 1024 bytes by default and up to 8192 (`zmodemBlockSize`).
8. **ZMODEM resume.** A partial download lives as `<name>.part` in the downloads directory. When the sender sends ZCRESUM, or `resume` is set on our receiver, and `<name>.part` exists and is shorter than the announced size, the receiver answers ZRPOS(partial length) and appends. Without resume a new `.part` is made. Completed files are renamed from `.part` to the final unique name, so a finished file is never appended to. No CRC comparison of the existing part is made (ZMCRC is not implemented); this is the same trust lrzsz's `-r` gives. Cost if wrong: a corrupted resume if the remote file changed between attempts.
9. **Kermit.** Basic packets (MARK SOH, LEN, SEQ, TYPE, DATA, CHECK, EOL CR), long packets (LEN 0 with LENX1, LENX2, HCHECK, up to 9024), block checks 1, 2 and 3 (CRC-16/KERMIT), control prefixing (`#`), 8th bit prefixing (`&`, used when either side asks), repeat count prefixing (`~`), attribute packets (`1` exact length, `!` length in K, `#` date `yyyymmdd hh:mm:ss`, `"` type `B8`), with refusal by size. Sliding windows: implemented if Task 8 gets there, and reported as not done otherwise. The S packet and its ACK use check type 1; the negotiated type starts with the F packet. Text mode conversion is not done: files are binary both ways.
10. **File side.** Received names: the last path component after `/`, `\` and `:`; control characters and DEL become `_`; leading dots become `_`; trailing spaces and dots are removed; Windows device names (CON, PRN, AUX, NUL, COM1 to 9, LPT1 to 9, with or without extension) get a `_` prefix; empty becomes `download`; capped at 200 UTF-8 bytes keeping the extension. Name bytes that are not UTF-8 are read as CP437. Files are created with `O_CREAT|O_EXCL|O_NOFOLLOW` inside the downloads directory only; collisions become `name-1.ext`, `name-2.ext`. An announced size over `maxFileSize` (default 4 GiB) is refused; writing past the announced size or the limit fails the transfer. On cancel or failure the `.part` is deleted unless `keepPartialForResume` is set and the protocol can resume (ZMODEM). Every finished file reports its SHA-256 in the event log; every block is CRC or checksum checked by its protocol.
11. **Telnet.** Over a telnet session the engine sees bytes after `TelnetSession.receive` (IAC sequences removed, IAC IAC to 255) and its output goes through `TelnetSession.encode` (255 doubled). Binary transfers need BINARY in both directions; `TelnetSession.requestBinary()` asks for both, and `TelnetTransferChannel.isByteClean` says whether they are on. Without BINARY the RFC 854 CR NUL rule still round trips between two conforming ends, but servers differ, so the session warns. SSH and WebSocket channels are byte clean (WebSocket must use binary frames, opcode 2, never text frames); no wrapper is needed beyond passing bytes.
12. **Detection.** `TransferStartDetector` reports `zmodemReceive` on `**\x18B00` (the remote sends ZRQINIT: we should receive), `zmodemSend` on `**\x18B01` (remote rz is waiting: we should send), `kermitReceive` on a Kermit S packet (`SOH`, length, `SP`, `S`). XMODEM and YMODEM have no reliable start sequence from a sender and are started by the user. The pattern may be split across feeds.
13. **CLI.** `ansixfer` is a SwiftPM executable product of the AnsiCore package. It is not in `project.yml` and is never in the app bundle. Cost if wrong: none for the app.

## Review Focus

- Every protocol, both directions, every listed size, every byte value: SHA-256 equal (tests in `TransferInProcessTests`).
- Error injection: dropped, duplicated, corrupted and inserted bytes recover (or fail cleanly for YMODEM-G, which cannot recover by design).
- Hostile senders: path traversal names, absolute paths, control characters, device names, oversized announcements, more data than announced, a symlink planted at the `.part` path.
- Cancel: CAN sequences in both directions, partial file removed (or kept for resume when asked).

## Interfaces for the terminal plan

```swift
let session = FileTransferSession(direction: .receive, kind: .zmodem,
                                  options: TransferOptions(),
                                  sink: DownloadsDirectorySink(directory: downloads),
                                  clock: SystemTransferClock())
session.onOutput = { bytes in client.send(bytes) }            // raw bytes; the client telnet-encodes
session.onEvent = { event in log.append(event) }
session.onProgress = { p in bar.update(p.bytes, p.total, p.bytesPerSecond, p.eta) }
session.onFinish = { outcome in /* .completed([TransferredFile]) or .failed(reason) or .cancelled */ }
session.start()
// from the client's receive path, after telnet decoding:
session.feed(bytes)
// a 10 Hz timer:
session.tick()
// user presses Cancel:
session.cancel()
```

The terminal feeds every received data byte to a `TransferStartDetector` while no session runs; a `.zmodemReceive` match starts a receive session (with the bytes from the match on fed to it), `.zmodemSend` offers an upload panel.
