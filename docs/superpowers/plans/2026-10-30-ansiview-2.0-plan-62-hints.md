# AnsiView 2.0 Hints, Tooltips and Glossary Implementation Plan (item 62)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every term a newcomer meets in AnsiView (iCE colours, SAUCE, ZMODEM, PETSCII...) is explained in plain English: a searchable glossary window, Help menu search that finds glossary terms, a (?) hint beside jargon controls that opens the glossary, and a tooltip or accessible label on every button, checkbox, popup and segmented control, proven by a measured inventory.

**Architecture:** The glossary is data in AnsiCore (`Glossary.swift`, pure Foundation so it also compiles for iOS): a `GlossaryTerm` enum (one case per entry, so hints and related terms are checked by the compiler), `GlossaryEntry` (term, aliases, hint, explanation, related, where in AnsiView) and a ranked `Glossary.search`. The app adds `GlossaryWindowController` (search field, term list, detail with related term links), a Help menu item, an `NSUserInterfaceItemSearching` handler so the Help menu's search field lists glossary terms, and changes `Hint.button` to take a `GlossaryTerm`. An offscreen harness (scratchpad, not the repo) links the real App and Shared sources, opens every window through its real entry point with window ordering swizzled off, walks the view hierarchies (and SwiftUI accessibility trees) and counts controls with and without tooltips; it runs before and after the sweep.

**Tech Stack:** Swift 5 mode, Swift Testing (AnsiCore), AppKit, SwiftUI commands, XcodeGen, String Catalogs (SWIFT_EMIT_LOC_STRINGS, `Packaging/sync-strings.sh`).

**Spec:** coordinator brief for checklist item 62 (owner: "hints should be there, for things, like what is ice, etc.."), `docs/STUDIO-CHECKLIST.md` row "Context sensitive help, tooltips, glossary".

## Review Focus

1. A search with odd input (empty, mixed case, "ice colors" American spelling, "z-modem", a trailing space) must still find the right entry or show everything: tests `searchIgnoresCaseAndSpelling`, `emptySearchListsEverything`.
2. A related term or hint pointing at an entry that does not exist would show an empty page: `GlossaryTerm` cases make it a compile error; test `everyTermHasExactlyOneEntry`.
3. Hint popovers whose text is long must still offer the glossary and not leak the long text into the tooltip (tooltip is the entry's one line hint): harness check, tooltip length rule.
4. Help menu search with no match must not crash or list junk: test `searchWithNoMatchIsEmpty`; handler called directly in the harness.
5. Opening the glossary twice, or from a hint while it is open, must reuse one window and select the term: harness check (`GlossaryWindowController.current` identity, selected row).

## Rulings

1. Glossary text is English data in AnsiCore, like `AnimationHelp` and `ImageImportHelp` already are; AnsiCore has no String Catalog. The window chrome strings are in the app catalog. Localizing glossary text later means moving it to a catalog (cost if wrong: one more pass of extraction, no API change).
2. "Accessible label" for the inventory: a tooltip, an explicit `accessibilityLabel`, or (buttons and checkboxes only) a visible title. Popups and segmented controls need a tooltip or explicit label, because their visible text is the current choice, not what the control is for.
3. Hint buttons reference a `GlossaryTerm`; free text hints are gone. A hint may add a short sentence specific to its window above the glossary hint.
4. Help menu search uses `NSApp.registerUserInterfaceItemSearchHandler` (documented AppKit API, works in SwiftUI life cycle apps); choosing a result opens the glossary on that term; "Show All Help Topics" opens the glossary with the search text.
