# AnsiView 2.0: Transports (SSH, WebSocket, RLogin) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline) with superpowers:test-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Owner brief section 9 "Transports" (the owner chose "Telnet, SSH and WebSocket"; RLogin is the small extra): the BBS terminal connects over telnet, raw TCP, SSH, WebSocket (ws and wss) and RLogin, through one byte clean duplex channel that the later file transfer work (X/Y/ZMODEM, Kermit) can run over.

**Architecture:** AnsiCore gets the transport abstraction and everything that needs no third party code: `Transport.swift` (`BBSTransport` protocol, `TransportSettings`, the Network.framework `TCPTransport`), `RLogin.swift` (RFC 1282 handshake bytes, the server's answer, `RLoginTransport` over TCP), `WebSocketTransport.swift` (`URLSessionWebSocketTask`, URL building, subprotocols, error mapping), `KnownHosts.swift` (trust on first use store in OpenSSH `known_hosts` format, SHA256 fingerprints like OpenSSH), `SSHKeyFile.swift` (OpenSSH and PEM private key files, including passphrase protected ones: bcrypt_pbkdf with Blowfish, AES-CTR/CBC by CommonCrypto) and `Blowfish.swift`. `BBSClient` keeps its public API (the terminal and the tests use it) and runs a telnet layer over any transport when the settings ask for it. The app target gets `App/SSHTransport.swift` (swift-nio-ssh client: PTY, shell, window change, password / empty password / public key auth, host key check) and the host key alerts. `BBSEntry` gains the per protocol fields; the retro entry editor shows only the fields of the chosen protocol.

**Tech Stack:** Swift 5 mode, Swift Testing, Network.framework, URLSession, CryptoKit, CommonCrypto, swift-nio-ssh 0.15.1 with swift-nio 2.104.0 (app target only), XcodeGen.

## Rulings

1. **One transport protocol in AnsiCore, SSH injected from the app.** `BBSTransport` (open, write, resize, close; callbacks opened, bytes, closed with a `BBSConnectionError?`) is implemented by `TCPTransport`, `RLoginTransport` and `WebSocketTransport` in AnsiCore and by `SSHTransport` in the app (it needs NIO). `BBSClient(host:port:mode:...)` keeps working; a new `settings:` and `transport:` pair lets the app hand in the SSH transport. A client asked for SSH without a transport fails with a plain message. Cost if wrong: a fourth library transport has to be added in the app as well.
2. **Byte clean channel for file transfers.** `BBSClient.send(_:)` and `onData` carry arbitrary bytes on every transport: SSH (channel data), WebSocket (binary frames) and RLogin (after the handshake) pass bytes unchanged; telnet doubles 0xFF and strips IAC commands on receive, and turns CR into CR NUL unless BINARY is on for that direction. The transfer integration must therefore ask for BINARY both ways before a transfer on telnet (the session already offers it and accepts the server's), and must not use telnet inside WebSocket without the same care. `BBSClient.isByteClean` tells the transfer code whether the current session needs that care. Cost if wrong: a telnet transfer with BINARY off corrupts CR bytes; the transfer code checks the flag first.
3. **Protocol choices and default ports.** `ConnectionMode` gains `ssh` (22), `webSocket` (80, or 443 with TLS), `rlogin` (513); telnet and raw stay 23. Switching the protocol in the editor moves the port to the new default only when the port still holds the old protocol's default. Old entries decode unchanged; an older app reading a new protocol value falls back to telnet (its decoder already ignores unknown values).
4. **SSH.** A session channel with a `pty-req` (term = the entry's terminal type, columns, rows), `shell`, and `window-change` on every resize. User name: the entry's username, or `guest` when empty (SSH needs one; most BBSes take any name and ask again in their own login screen). Authentication order: public key (when a key file is chosen), then password (the Keychain password, or the empty password when none is saved: many BBSes accept it), then `none`. Keyboard interactive is not offered because swift-nio-ssh has no such method; servers that only allow it fail with a message that says so. Key files: OpenSSH format (Ed25519, ECDSA P-256, P-384, P-521; unencrypted or passphrase protected with bcrypt and aes256-ctr, aes128-ctr, aes256-cbc, aes128-cbc) and PEM `EC PRIVATE KEY` / `PRIVATE KEY` (ECDSA). RSA keys are refused with a message: swift-nio-ssh cannot sign with RSA. The key file is kept as an app scoped security bookmark (existing `files.bookmarks.app-scope` entitlement); its passphrase is a Keychain item (`account` = `ssh-key-passphrase:` plus the username) next to the password. Cost if wrong: a user with only an RSA key makes an Ed25519 key (`ssh-keygen -t ed25519`).
5. **Host keys: trust on first use.** Known hosts live in `Application Support/AnsiView/known_hosts` in the app container, OpenSSH format (`host keytype base64`, `[host]:port` when the port is not 22). The fingerprint is shown like OpenSSH: `SHA256:` plus unpadded base64 of the SHA-256 of the key blob. First connection: an alert with the host, key type and fingerprint (Trust and Connect, Cancel), unless the entry's `Trust new host key` is on, in which case the key is saved without asking. A key that differs from the saved one: a critical alert that names both fingerprints and refuses the connection; its second button forgets the saved key so the next connection asks again (no way to connect with a changed key in one step). Cost if wrong: one more click after a sysop changes keys.
6. **WebSocket.** `URLSessionWebSocketTask` (no dependency) to `ws://host:port/path` or `wss://...` (TLS by URLSession, system trust). Data is sent as binary frames; received binary frames are passed on and text frames are passed on as their UTF-8 bytes (some bridges send text). The subprotocol field is a comma separated list sent in `Sec-WebSocket-Protocol` (empty sends none; common values `telnet`, `binary`). "Telnet inside" runs the telnet layer over the WebSocket stream for bridges that carry raw telnet (fTelnet style proxies, websockify in front of a telnet BBS). Errors: TLS failures, an HTTP answer instead of an upgrade (with its status code), host not found, refused, timed out. Cost if wrong: a bridge that wants text frames gets binary; a later option.
7. **RLogin (RFC 1282).** On connect: `NUL client-user NUL server-user NUL terminal/speed NUL`; the server's first byte NUL means accepted, anything else is the server's error text and the connection ends with it. Terminal = the entry's terminal type in lower case, speed 38400 when the line is unlimited, else the entry's simulated speed. Client user: the field, or the username when empty; server user: the field, or the username when empty. Window size: not sent. The server asks for it with TCP urgent data (an out of band 0x80), and Network.framework gives no access to urgent data, so the request cannot be seen; sending the `FF FF s s` cookie unasked would put those bytes into the input of servers that do not expect it. The sandbox cannot bind a privileged source port (below 1024), which RFC 1282 servers on Unix use to trust the client; BBS RLogin servers (Synchronet, Mystic) accept any source port. After the handshake the stream is byte clean. Cost if wrong: a BBS that wants the window size uses its default 80x24.
8. **SyncTERM import.** `SSH` and `SSHNA` (SSH without authentication: no password) import as SSH, `RLogin` as RLogin; `RLoginReversed`, `TelnetS`, `Modem`, `Serial`, `Shell`, `MBBSGhost` and others are still skipped and counted. SyncTERM has no WebSocket type.
9. **Editor fields.** Connection section: Protocol cycles Telnet, Raw TCP, SSH, WebSocket, RLogin; then only the chosen protocol's fields: SSH (Key file, Forget key file, Key passphrase, Trust new host key), WebSocket (Secure wss, Path, Subprotocols, Telnet inside), RLogin (Client user, Server user). Each has a one or two sentence hint. Changing the protocol rebuilds the form at once.
10. **Error messages per transport** (`BBSConnectionError` gains cases): authentication failed (SSH, with the methods the server allows), host key changed, host key not trusted, algorithm mismatch (the server only offers SSH methods AnsiView cannot use yet: names the likely cause), TLS failure, HTTP upgrade refused (status), RLogin refused (server text), SSH unavailable. Each says what happened and what to try.

## Review Focus

- A changed host key never connects (test `changedKeyIsRefused`), and `Trust new host key` never accepts a changed key.
- Fingerprint text identical to `ssh-keygen -lf` for the same key (test fixtures made with ssh-keygen).
- Key file decryption: right passphrase decrypts, wrong one gives `wrongPassphrase` (checkints), RSA refused (fixtures from ssh-keygen).
- RLogin handshake bytes exact; an error answer ends the session; data after the NUL in the same packet is kept.
- Passphrases and passwords never in JSON or exports.
